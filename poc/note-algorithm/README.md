# noteseek

note の配信 (レコメンド / 検索 / タグ) を観測し、
「記事がより読まれるための施策」がデータで裏づけられるかを判定する POC。

調査の背景と設計判断は
[design/specifications/008_202609060300_note配信アルゴリズム調査とPOC設計.md](../../design/specifications/008_202609060300_note配信アルゴリズム調査とPOC設計.md)
を参照。

## この POC が答える問い

1. note の配信面に載る記事を、外部から観測できる特徴量で予測できるか
2. できるなら、書き手が動かせる要素のうち何が効いているか
3. その結果は、下書き段階の助言として使える精度か

答えられない問いも明示しておく。ビュー数は自分の記事以外取得できないため、
本 POC はビュー数を直接扱わない。代理指標を 2 本立てる。

- 露出の代理: ハッシュタグ新着タブの記事のうち、人気 / 急上昇タブにも現れたか
- 反応の代理: スキ数 (対数変換)

## セットアップ

```bash
cd poc/note-algorithm
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

依存は `requests` のみ。統計処理とベクトル化は標準ライブラリで実装している。

## 使い方

### 0. 実装の検算 (ネットワーク不要)

既知の係数を仕込んだ合成データで、分析器が信号を復元できるかを確認する。

```bash
python -m noteseek selftest
```

`SELFTEST: PASS` が出なければ、実データを取る前に実装を直す。

### 1. API の疎通確認

利用するエンドポイントは note が公式に文書化したものではない。
収集前に、現在も生きているかを必ず確認する。

```bash
python -m noteseek probe --tag AI
```

### 2. 収集

```bash
python -m noteseek collect --tags AI 生成AI 個人開発 --out data/corpus.jsonl
```

ハッシュタグごとに新着タブ (母集団) と 人気 / 急上昇タブ (露出ラベル) を引く。
呼び出し間隔の下限は既定 1.5 秒。`--interval` で変更できるが、短くしない。

### 3. 分析と判定

```bash
python -m noteseek analyze --corpus data/corpus.jsonl --out report.md
```

判定は 4 値。

| 判定 | 意味 |
|---|---|
| USABLE | 露出・反応とも、フォロワー数のみのベースラインを超えて予測できた |
| PARTIALLY_USABLE | 片方のみ。合格した側の指標に絞って運用する |
| NOT_USABLE | この特徴量セットでは説明できない |
| INSUFFICIENT_DATA | 件数不足 (60 件未満) |

終了コードは USABLE / PARTIALLY_USABLE で 0、それ以外で 2。

### 4. 下書き診断

```bash
python -m noteseek advise \
  --corpus data/corpus.jsonl \
  --draft article.md \
  --tags 生成AI プロンプト
```

出力されるもの。

- 予測反応スコアのコーパス内順位
- トピック適合度 (topic fit) と母集団内順位
- 露出率リフトの高い未使用タグ (件数と実測率つき)
- タイトル所見
- 投稿時間帯別の実測露出率
- 上位記事の語彙のうち本文に不足しているもの

## 方法論上の要点

実装で意図的に守っている点を挙げる。これを崩すと結論が壊れる。

### 母集団は新着タブから取る

人気タブの記事だけを集めて共通点を探す設計は、生存者バイアスで破綻する。
同じ特徴を持ちながら露出されなかった記事が視界に入らないためである。
新着タブを母集団に取り、そこからの昇格を陽性とする。

### 効果は偏相関で読む

フォロワー数はスキ数とも露出とも強く相関する。統制せずに単純相関を取ると、
あらゆる特徴量がフォロワー数の影を拾う。

特徴量を「統制変数」(フォロワー数・投稿数・経過日数) と
「施策変数」(タイトル・本文・タグ・見出し画像・投稿時刻・トピック適合度) に分け、
施策変数は統制変数で残差を取った後の偏相関で評価する。
レポートには単純相関と偏相関の両方を出す。

### トピック適合度はトピックごとに測る

note は 2026-02 の刷新で、LLM が本文を読んでトピックへ分類する方式に移行した。
POC はこれを、収集元ハッシュタグごとの上位記事重心とのコサイン類似度で代理する。

複数タグを混ぜたコーパスで単一の重心を取ってはいけない。
「どのトピックにも中くらい似ている記事」が高評価になり、指標として無意味になる。
`advise` も、下書きが属するトピックにコーパスを絞ってから助言する。

### ベースライン超えを合格条件に入れる

フォロワー数だけを見たモデルに勝てない結果は、
記事側の工夫に意味があることを何も示していない。

### 負の対照を置く

完全にランダムなコーパスで USABLE が出ないことをテストで固定している
(`tests/test_pipeline.py::test_pure_noise_is_not_reported_as_usable`)。
これが通らない判定器は、実データで USABLE が出ても信用できない。

## 構成

| ファイル | 役割 |
|---|---|
| `noteseek/httpclient.py` | レート制限・再試行・ディスクキャッシュ |
| `noteseek/api.py` | note 非公式 API クライアント。候補 URL の生存判定つき |
| `noteseek/schema.py` | v1/v2/v3 と snake/camel の揺れを正規化 |
| `noteseek/collect.py` | 観測設計 (新着 = 母集団、人気/急上昇 = 陽性) |
| `noteseek/text.py` | 文字 N-gram TF-IDF、コサイン、N-gram の語への復元 |
| `noteseek/features.py` | 特徴量。統制変数と施策変数の分離 |
| `noteseek/stats.py` | 相関、Ridge、偏相関、AUC、NDCG |
| `noteseek/analyze.py` | 交差検証と POC 判定 |
| `noteseek/advise.py` | 下書き診断 (アプリに載せる機能本体) |
| `noteseek/fixtures.py` | 既知の係数を仕込んだ合成コーパス |

## 制約

- note の API は非公式であり、予告なく変更・廃止される
- レコメンドはバッチ寄りのため、公開直後の記事は配信面に反映されていない
- ビュー数・読了率・外部流入は外部から観測できない
- スキや フォローの自動化は実装しない。規約違反であり note の方針とも逆行する
