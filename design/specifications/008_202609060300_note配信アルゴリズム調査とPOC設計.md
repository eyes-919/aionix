# note 配信アルゴリズム調査と POC 設計

作成日: 2026-09-06

## 1. この文書の目的

note-mcp-automation に「記事がより読まれるための機能」を追加するにあたり、
note の配信 (レコメンド / 検索 / タグ) がどう動いているかを調査し、
その知見が実装に足るかどうかを POC で判定するための資料である。

対象読者は、この機能を実装する担当者。

結論を先に置く。

- note の配信ロジックは非公開であり、正確な再現は不可能である
- ただし 2026-02 の公式発表により、配信の主軸が「本文内容の LLM 解析」に
  移ったことは一次情報で確認できる
- したがって施策として意味があるのは「トピック適合度を上げること」であり、
  スキ稼ぎや相互フォローではない
- この仮説は観測可能である。観測設計と検証コードを POC として実装した

## 2. 一次情報 (note 公式)

### 2.1 2026-02 レコメンドエンジン刷新

note は 2026-02-12 にレコメンドエンジンとカテゴリページを刷新した。
公式が明示している内容は次のとおり。

| 項目 | 内容 |
|---|---|
| 中核技術 | LLM を用いた自動タグ付け。記事本文を解析しカテゴリ / トピックへ分類する |
| 粒度 | 「フード」「旅行」等の大分類から、「和食」「ドイツ旅行」等のトピック単位へ細分化 |
| カテゴリ数 | 大幅増 (ライフスタイル、ビジネス、子育て、小説など) |
| 効果 (公式値) | 2026-01 は前年同月比でカテゴリページ内の記事表示数 4.3 倍、記事閲覧数 2.2 倍、note 内回遊 1.5 倍 |
| 方針 | 「フォロワーが少なくても、良い記事なら必要な人に届く」 |

これが本調査で最も重要な事実である。

配信の入力が「フォロワー数 / スキ数 / SNS 拡散力」から
「記事本文が何について書かれているか」へ移ったということは、
施策の対象が **記事の外側 (拡散行動)** から **記事の中身 (語彙と主題の一貫性)** に
移ったことを意味する。

### 2.2 機械学習基盤

note の ML チームは以下を公開している。

- 記事の分散表現 (Doc2Vec) を保存する基盤を持つ
- faiss のインデックスで近傍記事を検索し、関連記事レコメンドに使う
- SageMaker Training でモデル学習、SageMaker BatchTransform で
  推薦対象ユーザごとの推薦記事リストを事前計算する

つまりレコメンドはリアルタイム計算ではなくバッチ寄りである。
公開直後に即座に配信面へ乗るとは限らず、反映に遅れが出る前提で観測する必要がある。

### 2.3 note が公開しないと明言している部分

note ヘルプセンターは、検索結果の「人気 / 急上昇 / 新着」の判定基準について
**不正防止のため公開していない** と明記している。

したがって「人気タブの基準はスキ 10 件」といった巷の断定はすべて推測である。
本 POC はこれらを仮説として扱い、データで否定できるようにする。

## 3. 二次情報 (実務者による観測) と、その信頼度

調査記事で繰り返し語られている主張を、検証可能性で分類する。

| 主張 | 出所 | 検証可能性 | 本 POC での扱い |
|---|---|---|---|
| 表示順は「関連性 x エンゲージメント x アカウント信頼度」 | 複数の考察記事 | 中 | 特徴量として分解して投入 |
| 読了率が重視される | 考察記事 | 低 (外部から観測不能) | 観測不能として除外。本文長で代理 |
| 外部流入が重視される | 考察記事 | 低 (外部から観測不能) | 除外 |
| コメント数の寄与は小さい | 考察記事 | 中 | comment_count を収集し確認可能にする |
| 適切なタグは 3-5 個。無関係タグの大量付与は逆効果 | 複数記事 | 高 | tag_count と tag_overlap を分離して検証 |
| 公開後 24 時間のスキ数が効く | 考察記事 | 中 | 経過日数を統制変数に入れて確認 |
| 「人気」= 約 1 ヶ月、「急上昇」= 約 1 週間のビュー / スキ増 | 考察記事 | 中 | 露出ラベルの定義に採用 |
| 相互スキ / 相互フォローは長期的に不利 | 考察記事 | 低 | 検証しない (観測手段がない) |
| 「今日の注目記事」は編集部の人手選定。1 日約 10 本 | 複数の実体験記事 | 高 | アルゴリズム対象外として明示 |

重要な注意点として、これらの出所の大半は note 上の記事であり、
「note で伸びる方法」という主題そのものが note で伸びやすいため、
生存者バイアスが強くかかっている。数値の断定は採用しない。

## 4. 観測できるもの / できないもの

施策を設計する前に、外部から何が測れるかを確定させる。

| 指標 | 外部取得 | 備考 |
|---|---|---|
| ビュー数 | 不可 | 自分の記事のダッシュボードのみ。他人の記事は取得できない |
| スキ数 | 可 | 一覧 API に含まれる |
| コメント数 | 可 | 同上 |
| 読了率 | 不可 | note 内部指標 |
| 公開日時 | 可 | |
| ハッシュタグ | 可 | |
| 見出し画像の有無 | 可 | |
| 有料 / 無料 | 可 | |
| フォロワー数 | 可 | |
| 人気 / 急上昇タブへの掲載 | 可 | タブ別に一覧を引けば差分で判定できる |

「より記事を見られる機能」を作るのに、肝心のビュー数が取れない。
これが本テーマの最大の制約である。

そこで代理指標を 2 本立てる。

1. **露出の代理**: ハッシュタグの新着タブに出た記事のうち、
   人気 / 急上昇タブにも現れたか (二値)
2. **反応の代理**: スキ数 (対数変換)

1 が本命である。note が「この記事を配信面に載せる」と判断した結果そのものを
観測しているため、ビュー数の代理として妥当性が高い。

## 5. 観測設計

### 5.1 生存者バイアスを避ける

やってはいけない設計は「人気タブの記事を集めて共通点を探す」ことである。
これは露出された記事の特徴しか見ておらず、
同じ特徴を持ちながら露出されなかった記事が視界に入らない。

本 POC の設計は次のとおり。

```
母集団 = ハッシュタグの「新着」タブに出た記事 (露出前の候補プール)
陽性   = そのうち「人気」または「急上昇」タブにも現れた記事
陰性   = 新着にしか現れなかった記事
```

これで「露出される記事の特徴」を見る。

### 5.2 交絡の統制

フォロワー数は、スキ数とも露出とも強く相関する。
統制しないまま単純相関を取ると、あらゆる特徴量がフォロワー数の影を拾う。

そこで特徴量を 2 種類に分ける。

- 統制変数: フォロワー数、投稿数、公開からの経過日数 (記事単位では動かせない)
- 施策変数: タイトル、本文、タグ、見出し画像、投稿時刻、トピック適合度

施策変数の効果は、統制変数で残差を取った後の **偏相関** で読む。
単純相関は参考値としてのみ併記する。

### 5.3 トピック適合度の代理実装

note 本体は LLM で本文を読みトピックへ分類する。
POC でこれを再現する必要はない。必要なのは
「同じトピックの上位記事群と、この記事がどれだけ近いか」を測ることである。

- 文字 N-gram (2-3 gram) + TF-IDF でベクトル化
- 形態素解析器を使わない (環境構築コストと再現性のため)
- トピック (= 収集元ハッシュタグ) ごとに上位記事の重心ベクトルを作る
- 記事と自トピック重心のコサイン類似度を topic_fit とする

複数タグを混ぜたコーパスで単一の重心を取ってはいけない。
「どのトピックにも中くらい似ている記事」が高評価になり、指標として無意味になる。

## 6. データ取得手段

note は公開 API を提供していない。フロントエンドが使う JSON エンドポイントを
利用する形になる。

| 用途 | エンドポイント |
|---|---|
| キーワード検索 | `/api/v3/searches?context=note&q=&size=&start=` |
| ハッシュタグ記事一覧 | `/api/v3/hashtags/{tag}/notes?order=new\|popular\|hot&page=` |
| ハッシュタグ情報 | `/api/v2/hashtags/{tag}` |
| カテゴリ記事一覧 | `/api/v2/categories/{name}?sort=&page=` |
| 記事詳細 | `/api/v3/notes/{key}` |
| クリエイター記事一覧 | `/api/v2/creators/{urlname}/contents?kind=note&page=` |

制約と方針。

- 非公式であり予告なく変更・廃止される
- 記事一覧取得の一部は GraphQL へ移行が進んでいる
- v1 / v2 / v3 が混在し、同じ値が snake_case と camelCase の両方で返る
- 認証は行わない。公開情報のみを対象とする
- 呼び出し間隔の下限を設ける。既定 1.5 秒

実装側の対応。

1. エンドポイントは候補リストで持ち、200 を返したものを採用する
2. `probe` サブコマンドで、どの候補が現在生きているかを先に確認する
3. レスポンス形状の揺れは正規化層で吸収する

これにより「API が変わったのか、分析結果が変わったのか」を切り分けられる。

## 7. POC の判定基準

実装は `poc/note-algorithm/` に置く。

判定は、学習データへの当てはまりではなく **ホールドアウトでの予測性能** で行う。
過学習した係数を根拠に施策を打たないためである。

| 課題 | 指標 | 合格ライン |
|---|---|---|
| 露出モデル | 5-fold CV の out-of-fold AUC | 0.65 以上、かつフォロワー数のみのベースライン超え |
| 反応モデル | 5-fold CV の out-of-fold Spearman | 0.25 以上、かつ同ベースライン超え |
| 最低サンプル数 | 記事数 | 60 件以上 |

出力される判定。

- USABLE: 両方合格。施策の根拠に使える
- PARTIALLY_USABLE: 片方のみ。合格した側の指標に絞って運用する
- NOT_USABLE: この特徴量セットでは説明できない
- INSUFFICIENT_DATA: 件数不足

ベースライン超えを条件に入れているのが要点である。
「フォロワー数だけを見た場合」に勝てないモデルは、
記事側の工夫に意味があることを何も示していない。

## 8. 実装の自己検証

実データを取る前に、分析器そのものが正しいかを確認する必要がある。
既知の係数を仕込んだ合成コーパスを生成し、それを分析器が復元できるかを見る。

仕込んだ生成モデル (対数スケール)。

```
score = 0.80 * log1p(followers)
      + 2.20 * topic_fit
      + 0.45 * has_eyecatch
      + 0.60 * tag_overlap
      - 0.35 * is_paid
      + 0.30 * prime_hour
      + noise
```

`python -m noteseek selftest` が、この 4 つの主要信号を
すべて有意として検出し、判定 USABLE を返すことを確認済みである。

合わせて負の対照も置いている。完全にランダムなコーパスを与えたとき
USABLE を返さないことをテストで固定した。これが通らない判定器は、
実データで USABLE が出ても信用できない。

合成データは実データの代わりにはならない。判定の根拠は必ず実データで取る。

## 9. アプリへの実装方針

POC が USABLE または PARTIALLY_USABLE を返した場合、
note-mcp-automation の下書き準備フローに次のゲートを追加する。

```
記事HTML
 -> note review
 -> [追加] トピック診断ゲート
      - 競合トピックの特定
      - topic_fit スコアと母集団内順位
      - 露出率リフトの高いタグの提示
      - 上位記事の語彙のうち本文に不足しているもの
      - 投稿時間帯別の実測露出率
 -> HTML parser
 -> ... (以降は現行フロー)
```

設計上の制約を 2 つ置く。

1. **診断であって自動書き換えではない**
   タグや本文を自動で書き換えない。提示のみを行い、採否は書き手が決める。
   既存プロジェクトの `READY_FOR_HUMAN_PUBLISH` 境界と同じ思想である。

2. **根拠のない助言を出さない**
   すべての助言に、コーパス内の実測値 (件数、露出率、リフト) を併記する。
   「タグは 3-5 個が良い」のような通説は、そのコーパスで確認できた場合のみ出す。

## 10. やらないこと

- スキや フォローの自動化。規約違反であり、note の方針とも逆行する
- ビュー数の推定値をあたかも実測のように提示すること
- 「今日の注目記事」対策。人手選定であり、アルゴリズム施策の対象外
- note のレコメンドモデルそのものの再現

## 11. 残る検証ゲート

以下は実データがないと確定できない。実行は本人環境で行う。

1. `python -m noteseek probe` で現行エンドポイントの生存確認
2. 複数ハッシュタグで 60 件以上を収集し `analyze` を実行、判定を得る
3. 露出ラベルの妥当性確認。新着プールに対する人気 / 急上昇の昇格率が
   極端 (0% または 100%) になる場合は母集団の取り方を見直す
4. バッチ反映の遅延を踏まえ、同一タグを日をずらして 2 回以上収集し、
   ラベルが安定するか確認する
